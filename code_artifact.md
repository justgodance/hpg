# Правила разработки проекта "Game Marathon Board"

Этот документ описывает стандарты кодирования, архитектурные принципы и правила ведения проекта. Всем разработчикам (включая ИИ-агентов) необходимо строго следовать этим инструкциям.

## 1. Конфигурация и отсутствие "Магических чисел" (Magic Numbers)
Любые числовые значения, коэффициенты или таймауты **запрещено** хардкодить в бизнес-логике. Все они должны быть вынесены в `config.py` или `.env`.
*   **Примеры для выноса в конфиг:** 
    *   Вместимость доски (12 карточек).
    *   Время анимации колеса рулетки.
    *   Коэффициент инфляции (+20% в день) и хард-кап инфляции.
    *   Интервал HTMX-поллинга (10 секунд).
    *   Пороги вероятностей (7% на Санту, 3% на GOTY).
*   **Секреты:** Токены базы данных, секреты сессий и URL Discord Webhook должны храниться **только** в файле `.env`.

## 2. Работа с базой данных (SQLAlchemy & Alembic)
Так как экономика игры построена на конкурентных действиях, безопасность данных приоритетнее скорости:
*   **Защита от гонки данных (Race Conditions):** При любых операциях взятия квеста, покупки в магазине или обмена предметами использовать блокировку уровня строки: `with_for_update()`.
*   **Миграции:** Никогда не менять модели БД без создания миграции Alembic. Запрещено использовать `Base.metadata.create_all` в production-окружении.
*   **Сессии:** Использовать Dependency Injection (`get_db`) для передачи сессий базы данных в FastAPI роутеры.

## 3. Архитектура Frontend (HTMX + Tailwind)
*   **Никакого спагетти из JavaScript:** Вся логика должна лежать на бэкенде. Frontend должен быть максимально "тупым" и реактивным.
*   **Частичный рендеринг (Partials):** FastAPI эндпоинты, которые вызываются через HTMX, должны возвращать **только** небольшие HTML-фрагменты (partials), а не перерисовывать всю страницу целиком.
*   **OOB Swaps:** Для обновления сразу нескольких элементов на странице (например, обновление доски + обновление счетчика очков в профиле) использовать механизм `hx-swap-oob`.

## 4. Типизация и Валидация (FastAPI + Pydantic)
*   Код должен быть строго типизирован (Type Hinting). Не использовать `Any` без крайней необходимости.
*   Любые данные, приходящие от пользователя (например, ввод ПИН-кода или применение предмета), должны валидироваться через схемы `Pydantic`.
*   Соблюдать разделение: Pydantic-схемы для API, SQLAlchemy-модели для БД.

## 5. Проверка работоспособности кода (Тестирование)
*   После любого значимого обновления (добавление роутера, изменение логики HTMX) необходимо убедиться, что код запускается и работает без ошибок.
*   **Особое внимание к логам:** Ошибки 500 не должны скрываться HTMX-ом. Убедиться, что терминал FastAPI детально выводит трейсбеки.
*   Перед деплоем проверять работу доски в нескольких вкладках браузера одновременно (симуляция многопользовательской среды).

## 6. Ведение Learning Guide (Подготовка к собеседованиям)
Для подготовки к будущим собеседованиям на позицию Python/Backend разработчика, проект должен параллельно документироваться в файле `learning_guide.md`.
*   **Что туда писать:** 
    *   Почему был выбран FastAPI (асинхронность, ASGI, Pydantic).
    *   Как устроена защита от Race Condition (`with_for_update` в PostgreSQL).
    *   Как работает раздача статики и шаблонизация Jinja2.
    *   Паттерны деплоя (как проект настраивался на сервере: Gunicorn, Uvicorn, Nginx, Systemd).
*   **Правило для ИИ:** При внедрении любой сложной фичи, ИИ-агент обязан добавлять краткую техническую выжимку в `learning_guide.md` с объяснением концепции «под капотом».
